# Architecture review (14 Oct 2026)

A review of SCRD Utility Manager as it stands after six weeks of fast feature
work: how it fits together, what was wrong, what was fixed, and what is left.
Detailed design notes are in ARCHITECTURE.md.

## 1. How it fits together

```
Browser (React SPA, web/)  ──fetch /api/v1──┐
Telegram ── webhook /api/v1/telegram ───────┤
                                            ▼
                 Cloudflare Worker (server/src/worker.js), placed in Mumbai
                   └─ Hono app (app.js): authenticate → rate limit → body →
                      preHandler → route handler → JSON
                        ├─ routes/*.js        one module per area
                        ├─ telegram.js        bot commands, alerts, summary
                        ├─ agent.js           assistant (Claude) with tools that
                        │                     call the API as the user (asUser)
                        └─ reportImport.js    condition-report workbooks
                                            │ pg, per-request connections
                                            ▼
                 Hyperdrive (pool, origin limit 10) → Supabase session pooler
                 (15 clients) → Postgres (Mumbai)
```

- **Static files** (web/dist) are served by Cloudflare directly; only `/api/*`
  runs the Worker.
- **The same app runs on Node** (index.js, pooled connections, PGlite for
  development and tests).
- **Authentication:** a session cookie or a Bearer session token. Every
  request loads the user (role, technical flag, unit, units headed, scopes)
  in one query.
- **Authorisation is layered:**
  - the role rank (`hasRole`);
  - staff permissions (`allowed`);
  - the technical-only prefixes (`TECHNICAL_PREFIXES`);
  - per-row visibility in SQL (`projectVisible`, `workVisible`);
  - per-item access (`assertAccess`, `workAccess`).
- **Audit:** triggers record every change with `app.user_id` set inside
  `db.tx`.
- **Data in:**
  - the website;
  - Telegram commands and the assistant (through `asUser`, so the same rules
    apply);
  - condition-report workbooks uploaded by staff.

  Nothing outside the system connects since Fleet Manager was disconnected on
  14 Oct.

### A request, end to end (dashboard)

1. The browser calls `GET /api/v1/dashboard`. Cloudflare runs the Worker in
   Mumbai, next to the database.
2. `worker.js` opens a request scope (a set of up to 4 connections) and
   hands the request to Hono.
3. `authenticate` loads the session and user (1 query). Then the dashboard
   runs about 10 queries together: service counts, engines, reports, work,
   projects and interruptions. Each is filtered by what the user may see.
4. The JSON goes back to the browser, and the request scope closes its
   connections.

## 2. What was found

| # | Area | Finding | Impact |
|---|---|---|---|
| 1 | Performance | Every query opened a new database connection (`perRequestDb`): about 10 per dashboard load. | Connection setup dominated page time |
| 2 | Performance | `mvToday()` asked the database for the date before the dashboard, Electricity, engines and asset pages could start their real queries. | One wasted round trip per page |
| 3 | Performance | The island page ran its queries in 2 waves, the work order page in 4 steps, the project page in 6. | Extra round trips |
| 4 | Performance | The bot and assistant (`asUser`) wrote a session row and deleted it for every internal API call. | 2 writes per tool call; many per assistant answer |
| 5 | Performance | The web app was one 494 kB script (138 kB gzip), loaded before the first screen. | Slow first load on island connections |
| 6 | Reliability | A connection refused by the pooler could surface as an unhandled `error` event. | A failed request instead of a clean retry or error |
| 7 | Duplication | Work states existed in 4 copies, asset labels in 3, the settable statuses in 3, and the `'WO-' \|\| lpad(...)` ref formatting in about 12 places, SQL and JS. Copies had already drifted: the assistant's list lacked a work state, and a new status had to be added in 5 files. | Bugs when lists change |
| 8 | Duplication | "Today in the Maldives" was worked out 4 ways. "Update only the fields sent" was copied into 4 routes. | Inconsistency |
| 9 | Maintainability | `routes/projects.js` held projects, files and the whole task tracker (520 lines). | Hard to change safely |
| 10 | Scalability | Hyperdrive allowed 60 connections into a pooler that takes 15 (fixed 11 Oct: limit 10). | Outages under load |

Checked and **not** a problem:
- **Query plans and indexes:** the largest table has about 5,600 rows, and
  every hot filter is indexed (work by island, asset, unit, assignee and open
  status; sessions by hash; commenters by user). The database executes
  queries in milliseconds. Latency was round trips and connection setup.
- **SQL injection:** every value is a parameter. Fragments built in code
  (`Where`, `updateSet`, `refSql`) only use fixed column names.

## 3. What was changed

Behaviour is unchanged. 116 tests pass, 6 of them new.

- **Connections reused within a request** (`db-pg.js`, `worker.js`).
  - Each request has up to 4 connections. A query takes an idle one, and a
    connection handed back goes straight to a waiting query.
  - Broken connections are dropped. Pooler refusals are retried with backoff.
  - When the request ends, idle connections close at once and busy ones close
    as they are handed back.
  - Unit tests are in `test/db-pg.test.js`.
- **The bot acts as the user without sessions.** The user id rides in the
  internal call's environment under a `Symbol`, which no outside request can
  carry. It goes through the same `authenticate` checks, via `loadUser`.
- **No database round trip for the date:** `time.js` `localToday(tz)`.
- **Fewer round trips:** the island, work order and project pages each run
  their queries together.
- **Shared vocabulary:** `domain.js` holds services, facility and asset
  kinds, asset statuses (all, settable, listed), and work kinds and states
  with labels. `format.js` holds `esc`, `workRef`, `projectRef`, `refSql`,
  `assetName` and `assetLabel`. Routes, the bot and the assistant use them.
- **`parsePatch()`** in http.js replaces four copies of "only the fields
  sent".
- **The tracker has its own module,** `routes/projectTracker.js`. It holds the
  schemas, the task, access and checklist routes, and `loadTasks` /
  `loadSites`.
- **Web:** pages load on demand (`React.lazy`, with `Suspense` inside the
  layout so the menu stays).
  - The first script is 291 kB (93 kB gzip), down from 494 kB (138 kB).
  - A page file that has gone after a deploy reloads through `CrashGuard`.

Measured from Malé against the live data, before → after (server path
through the same code):

| Page | Before | After |
|---|---|---|
| Dashboard | 2.9 s | 1.2 s |
| Water | 1.5 s | 0.7 s |
| Islands list | 0.75 s | 0.49 s |

On Cloudflare in Mumbai, each connection that's saved is a smaller amount of
time, but there are about 10 per page.

## 4. What is left (recommended, not done)

In order of value:

1. ~~**Files in Postgres.**~~ Done differently: the system no longer stores
   files at all; projects, documents and surveys link to Microsoft 365
   (migration 049).
2. **Login rate limiting is per Worker isolate** (in memory). Under load
   Cloudflare runs many isolates, so password guessing is only blunted. Add a
   Cloudflare rate-limiting rule on `/api/v1/auth/login`, or keep counters in
   the database.
3. **telegram.js (580 lines)** mixes the Telegram transport, the command
   parser, the morning summary, account linking and alerts. Split it into
   `telegram/{transport,commands,summary,linking}.js`. The commands' tests
   already cover the behaviour.
4. **The vocabulary is held twice:** server `domain.js` and `web/src/format.js`.
   Serve it once (e.g. `GET /meta`) or generate the web copy at build time, so
   a new status is added in one place.
5. **The audit log has no retention.** It's about 5,600 rows after six weeks;
   at that rate it stays small for years. Add a yearly archive if it ever
   matters.
6. **CSRF:** cookie-authenticated writes are refused when their `Origin` is
   foreign, but allowed when there is no `Origin` header (old browsers and some
   tools). Browsers send it on these requests and SameSite cookies cover the
   rest, but requiring it would close the gap.
7. **Session lookup on every request** is one query (about 2 ms in Mumbai).
   A short per-isolate cache would save it. Don't do this unless needed:
   changes to roles and access must apply at once.
